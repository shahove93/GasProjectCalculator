## Goal

Make the existing FastAPI + frontend application run as a packaged Windows x64
desktop application with a native window, without requiring Python, a console,
or manual server start. Keep the developer uvicorn path and all GSV behavior
unchanged.

Proposed technology (approved architecture): PyInstaller (onedir build) and
pywebview (EdgeChromium/WebView2). Do not add a new architecture decision.

## Required behavior

1. Packaged application (PyInstaller onedir, windowed/no console) starts its
   FastAPI backend bound to `127.0.0.1` only on an available port.
2. Port conflict is handled safely: if a candidate port is busy (including 8000),
   choose another free localhost port; never fail silently and never bind a
   non-loopback interface.
3. The native pywebview window is shown only after the backend answers a
   readiness request; first launch waits for readiness with a bounded timeout.
4. All three modes work through the packaged app: GET `/`, POST `/calculate`,
   POST `/calculate/gsv`, POST `/calculate/combined` (same bodies/results as the
   developer server).
5. Closing the window exits the application and its backend; no listening port
   and no leftover child process remains. Cover both an in-process server thread
   and a child process if the chosen design uses one.
6. A clear, understandable error is shown if launch fails (e.g. WebView2
   unavailable, backend bind/start failure); no raw console traceback is the
   only output.
7. Developer path `.\.venv\Scripts\python.exe -m uvicorn app.main:app` still
   works and the full unittest suite still passes.
8. Provide a minimal, documented diagnostics/self-test flag on the packaged exe
   so automated evidence can discover the chosen port and close the window
   without manual interaction (for example `--port-file` and
   `--auto-close-seconds`, or an equivalent bounded test hook). The hook must not
   change normal user behavior.
